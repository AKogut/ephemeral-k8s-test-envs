# Security

## Scope

This repository is a demonstration of ephemeral test environments. The
application it deploys — an auth service, a notes API and a gateway — exists to
give those environments something real to run and test. **It is not intended for
production use**, and it stores nothing of value: every account it creates is
generated by a test, lives for seconds, and is destroyed with its namespace.

## Reporting a vulnerability

Open a [security advisory](https://github.com/AKogut/ephemeral-k8s-test-envs/security/advisories/new)
rather than a public issue.

Findings in the Kubernetes and CI configuration are the most interesting ones —
an over-broad RBAC rule, a missing security context, a token mounted where it is
not needed, a teardown path that can leak. Those are the parts of this repository
meant to be exemplary.

## Deliberate trade-offs

Documented rather than hidden, because a reviewer should be able to tell the
difference between a decision and an oversight:

| Choice | Reason | Where it is argued |
|---|---|---|
| `notes-service` holds the JWT signing secret, so it *could* mint tokens | Shared-secret HS256 instead of JWKS; both services are in one trust boundary and deploy together | [ADR 0003](docs/adr/0003-shared-secret-jwt.md) |
| scrypt cost lowered from 2^14 to 2^12 in environments | Throwaway accounts; the application default stays 14 and production refuses to start without an explicit secret | [ADR 0005](docs/adr/0005-test-tuned-kdf-cost.md) |
| `networkPolicy.enabled: false` by default | kind's CNI does not enforce NetworkPolicy — shipping it on would look like isolation while enforcing nothing | `values.yaml` |
| No TLS between services | Everything is inside one namespace on a throwaway cluster; a service mesh would be scope well beyond the point | — |
| No rate limiting | No untrusted callers exist | — |

## What the project does do

These are defaults worth copying:

- **Non-root containers** — `runAsNonRoot`, uid 1000, `fsGroup` set for volumes.
- **Read-only root filesystems** everywhere, with explicit `emptyDir` mounts for
  the few paths that need writing.
- **All Linux capabilities dropped**, `allowPrivilegeEscalation: false`,
  `seccompProfile: RuntimeDefault`.
- **No service account token in application pods.** A proxy and two CRUD services
  have no business holding a cluster credential.
- **Least-privilege RBAC** for the two workloads that do use the API: the
  aggregator may `get` exactly one named Job; the teardown Job may `delete`
  exactly one namespace, pinned with `resourceNames`.
- **Secrets are never passed on a command line.** The chart generates a signing
  key per release and preserves it across upgrades; `jwt.existingSecret` is there
  for anyone supplying their own.
- **Images pinned to a digest-stable tag** and built from a slim base, with the
  build toolchain confined to discarded stages.
- **No package manager in any runtime image.** Every entrypoint is `node`;
  `node_modules` arrives prebuilt from an earlier stage. npm and corepack are
  deleted from the final layer, which removes npm's vendored copy of `node-tar`
  along with them.

## Vulnerability scanning

Every image is scanned with Trivy on every pull request, in the job that builds
it. Two passes, and the difference between them is the policy:

| Pass | Severity | Fails the build | Where it goes |
|---|---|---|---|
| Record | `HIGH`, `CRITICAL`, fixable only | no | GitHub code scanning, one category per image |
| Gate | `CRITICAL`, fixable only | **yes** | the job log |

Gating on `HIGH` would turn the pipeline red on a Tuesday because an advisory
landed in a base image nobody touched, and a check that breaks on its own teaches
people to merge past it. `--ignore-unfixed` is the same argument from the other
side: a vulnerability with no available fix is information, not a decision anyone
can act on in this repository.

The first run of this scan was not decorative. It found five fixable criticals in
every image — two in `libgnutls30` from a stale base tag, three in the `node-tar`
that npm vendors. Both are fixed:

| | Fixable CRITICAL | HIGH | MEDIUM | LOW |
|---|---|---|---|---|
| Before | 5 | 35 | 40 | 9 |
| Base image moved to Node 22.23.2 | 1 | 7 | 8 | 0 |
| npm removed from the runtime layer | **0** | **0** | **0** | **0** |

Removing npm does not make the images smaller — the files come from the base
layer and a later `rm` only writes a whiteout. What changes is the filesystem the
container actually runs with, which is what the scanner reads and what anyone
inside the container would find.

## Application-level behaviour the suite locks in

- Registration and login return **identical responses** for "no such user" and
  "wrong password", and login hashes a dummy password on the unknown-user path so
  the timing matches.
- Another user's note is **404, not 403** — 403 would confirm the id exists and
  turn the API into an id oracle.
- JWTs are checked for **issuer and audience**, not only signature, and the
  `alg: none` downgrade is rejected. All three are asserted in
  `tests/api/specs/notes-authz.spec.ts` and `auth-me.spec.ts`.
- Error bodies never contain a stack trace, an internal path or a `node_modules`
  reference — asserted in `resilience.spec.ts`.
- User input reaching SQL goes through parameterised statements, and `LIKE`
  wildcards in search terms are escaped with an explicit `ESCAPE` clause.
